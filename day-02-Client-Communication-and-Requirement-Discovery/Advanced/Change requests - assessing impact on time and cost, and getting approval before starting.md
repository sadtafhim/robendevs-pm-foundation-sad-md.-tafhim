
# Change Requests: Assessing Impact on Time and Cost, and Getting Approval Before Starting

## 1. What Is a Change Request?

A change request is a formal request to modify something that has already been agreed upon in a project.

It may involve adding new features, modifying existing functionality, changing designs, updating requirements, or adjusting deadlines.

For example, a client initially requests an e-commerce website with basic payment integration. During development, they request additional payment gateways, product reviews, and a wishlist.

Since these features were not included in the original scope, the project manager must evaluate their impact before allowing the team to start working on them.

**Main rule:** Every significant change must be assessed, discussed, and approved before implementation begins.

## 2. Why Is Change Request Management Important?

Without a proper change request process, projects can become difficult to manage.

Accepting additional requests without evaluating their impact can lead to:

- Increased development costs.
- Delayed deadlines.
- Unplanned workloads.
- Confusion about requirements.
- Poor software quality.
- Disagreements between clients and developers.

A proper process ensures that every change is evaluated before it affects the project.

## 3. What Can Be Considered a Change Request?

A change request can involve different parts of a project.

| Change Type | Example |
|---|---|
| New Feature | Adding a wishlist to an e-commerce website. |
| Existing Feature Modification | Changing the checkout process. |
| Design Change | Replacing an approved homepage design. |
| Technical Change | Switching to a different database. |
| Scope Change | Adding a mobile application to a website project. |
| Timeline Change | Moving the final delivery date. |
| Requirement Change | Changing how user authentication works. |
| Integration Change | Adding another payment gateway. |

The project manager must identify what is changing and how it affects the original agreement.

## 4. The Change Request Management Process

Every significant change should follow a structured process.

1. **Request Submission:** The client or stakeholder submits a request describing the proposed change.
2. **Request Review:** The project manager reviews the request to understand what needs to change and why.
3. **Impact Assessment:** The team evaluates its effect on time, cost, resources, scope, and quality.
4. **Discussion:** The project manager explains the estimated impact and possible alternatives to the client.
5. **Approval:** The authorized stakeholder approves or rejects the proposed change.
6. **Documentation:** The project manager updates the relevant project records.
7. **Implementation:** The development team starts working on the approved change.

## 5. Assessing the Impact on Time

Time impact refers to how much additional time is required to complete a requested change.

The project manager should consult the development team to estimate the time needed for design, development, integration, testing, and bug fixing.

**Example:**

A client requests an additional payment gateway for an existing e-commerce website.

| Activity | Estimated Time |
|---|---|
| Requirement analysis | 1 day |
| Payment gateway integration | 3 days |
| Testing | 2 days |
| Bug fixing | 1 day |
| **Total** | **7 days** |

The change requires approximately seven additional working days.

When estimating time, consider:

- Development effort.
- Design modifications.
- Testing requirements.
- Integration with external services.
- Dependencies on other features.
- Client review and approval time.

If the additional work cannot fit into the existing schedule, the project deadline may need to change.

## 6. Assessing the Impact on Cost

Cost impact refers to the additional money required to implement a requested change.

Additional work may require more developer hours, design work, testing, infrastructure, or third-party services.

**Example:**

A client requests a wishlist feature for an e-commerce website.

| Activity | Estimated Cost |
|---|---|
| UI/UX design | ৳5,000 |
| Frontend development | ৳12,000 |
| Backend development | ৳15,000 |
| Testing and QA | ৳5,000 |
| **Total** | **৳37,000** |

If the original project budget was ৳500,000:

| Description | Amount |
|---|---|
| Original Budget | ৳500,000 |
| Additional Cost | ৳37,000 |
| **Revised Budget** | **৳537,000** |

The project manager must communicate the additional cost and obtain approval before implementation.

When estimating cost, consider:

- Developer and designer working hours.
- Testing and QA effort.
- Additional infrastructure expenses.
- Third-party API or service fees.
- Additional project management effort.
- Maintenance and support requirements.

**Important:** Even a small feature can affect multiple parts of a system and create additional costs.

## 7. Assessing Other Project Impacts

Time and cost are not the only factors to consider.

A change can also affect:

| Area | What to Consider |
|---|---|
| Scope | Does it introduce new deliverables? |
| Quality | Could it introduce bugs or reduce reliability? |
| Resources | Are additional developers or designers needed? |
| Dependencies | Will existing features need modification? |
| Security | Does it introduce new security risks? |
| Maintenance | Will it make future maintenance more difficult? |

A proper impact assessment considers the overall effect of a change on the project.

## 8. Getting Approval Before Starting

After assessing a change, the project manager must present its impact to the client or authorized decision-maker.

The client should understand:

- What is changing and why.
- How much additional time is required.
- How much additional money is required.
- Whether the project deadline will change.
- How the change affects the existing scope.

The team should only begin implementation after receiving the required approval.

**Example: Change Request Proposal**

| Field | Details |
|---|---|
| Change ID | CR-005 |
| Requested Change | Add wishlist functionality |
| Reason | Improve customer experience |
| Time Impact | 5 working days |
| Cost Impact | ৳37,000 |
| Requested By | Client |
| Approval Status | Pending |
| Implementation Status | Not Started |

If the client approves the request, the project documentation is updated and development can begin.

If the client rejects it, the original project scope remains unchanged.

## 9. What Happens If the Client Rejects the Change?

Not every change request will be approved. The client may reject a request because of additional costs, delays, or low priority.

In that situation, the project manager should:

1. Record the rejection.
2. Keep the original scope unchanged.
3. Inform the development team.
4. Avoid implementing the rejected change.
5. Keep the request documented in case it is reconsidered later.

The project should continue according to the existing approved plan.

## 10. Change Request Documentation

Every significant change should be documented so the team can track what was requested, why it was requested, its impact, and whether it was approved.

A change request record should include:

- Change ID.
- Project name.
- Requested by.
- Request date.
- Description of the change.
- Reason for the change.
- Estimated time impact.
- Estimated cost impact.
- Priority.
- Approval status.
- Implementation status.

### Where Should Change Requests Be Stored?

- **Confluence:** Store detailed change request documents and approval records.
- **Jira:** Track change requests as issues or tasks.
- **Email:** Communicate proposals and obtain written approval.
- **Project Management Tools:** Track ownership, status, deadlines, and progress.

The important thing is to maintain one reliable record of the latest approved information.

## 11. Common Mistakes to Avoid

| Mistake | Why It Is a Problem |
|---|---|
| Starting work before approval | Creates disputes about payment and responsibility. |
| Not estimating additional time | Can cause unexpected delays. |
| Ignoring additional costs | Can exceed the project budget. |
| Accepting verbal requests without documentation | Creates confusion about what was approved. |
| Not consulting developers | Leads to inaccurate estimates. |
| Forgetting to update project documentation | Team members may follow outdated requirements. |
| Not recording rejected requests | Makes it difficult to track previous decisions. |
| Treating every change as urgent | Disrupts existing priorities and schedules. |

## 12. Key Takeaways

Change request management ensures that additional requirements are evaluated and approved before they affect the project.

Remember these five steps:

1. **Receive:** Understand and document the requested change.
2. **Assess:** Evaluate its impact on time, cost, scope, resources, and quality.
3. **Communicate:** Explain the impact and available options to the client.
4. **Approve:** Obtain confirmation from the authorized decision-maker.
5. **Implement:** Update project documentation and start the approved work.

**Remember:** Never let the development team start significant additional work just because a client requested it. First understand the request, assess its impact, communicate the consequences, and obtain approval.
